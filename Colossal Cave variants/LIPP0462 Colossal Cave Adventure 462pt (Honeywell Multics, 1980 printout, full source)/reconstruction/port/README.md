# Adventure 1.2 (462 points), Honeywell's Phoenix Multics, 1980 (LIPP0462) - Windows console port

`adv462.exe` plays the game; start `run.bat`. It needs `adventure.newgame` beside it: the database already read
in, which the game makes itself on its first run and `build.bat` makes for you.

The game is Jim Lippard's: his transcription of the 1980 listings, corrected and completed, in
`../src_original/adv462/` (see `../README.md`). His Unix port, `unix/adv462.f`, is generated by his
`mkunix.py` from the Multics master copy and already builds with MinGW-w64 gfortran. This port takes it as it
is, and adds:

- `src/mkwin.py`, which writes `.build/adv462w.f` from `unix/adv462.f` with one fix and three changes. Each
  edit asserts how many times its text occurs, and each is marked `windows port` in the output;
- `src/adv462_win.c`, the routines Palter's program leaves to the site (`addr`, `size`, `ldcomn`, `svcomn`,
  and `advdat`, the path of the database), adapted from Lippard's `unix/adv462_util.c` for Windows.

## Building

`build.bat` runs `build.sh` in WSL. It needs Debian's `gfortran-mingw-w64`, `gcc-mingw-w64` and `python3`
there. The program is cross-compiled as a native, statically linked Windows console program that imports only
`KERNEL32.dll` and `msvcrt.dll`, so it does not need WSL (or anything else) to run.

In an MSYS2 or Git Bash shell with a native MinGW-w64 `gfortran` on PATH, `build.sh` works as it is. The
compiler flags are those of the Unix Makefile: `-fdefault-integer-8` gives the 36-bit Multics integers room,
and `-std=legacy -fdec-char-conversions -ffixed-line-length-none -fno-range-check` let gfortran accept 1970s
Fortran.

The last step runs the new program once and answers the wizard's questions, as the Unix Makefile does. This
is Palter's own first-time setup: the program reads `adventure.data`, reports its table space, and saves the
fresh game as `adventure.newgame`. `ADV462_CLOCK` is set for that run so every build writes the same image.

## The fix: the vial and the mushroom

`vial` and `mushroom`, the object numbers of two of Platt's things, are set when the database is read. But
they are in no common block, and `adventure.newgame` is made of the common blocks. So every game, which
starts from that image, had both undefined: they held whatever was on the stack.

- On Windows, `vial` came out as 895 (the vial is object 81), so THROW VIAL never recognised the vial, and
  the slime could not be dealt with that way.
- `mushroom` came out as a different 13-digit number in every run. A bare EAT, EAT MUSHROOM and the end of
  the mushroom's strength (`call move(mushroom,160)`) looked at a random place in memory.
- On Linux the same program crashed at a bare EAT in 12 of 200 random runs.

The 1980 listing has the same common block. Lippard fixed the same slip for `mushturn` ("mushturn was not in
the block"). `vial` and `mushroom` now go beside it, before `djinn`, which ends the saved area. The image
grows by the two words, and a game now starts with `vial`=81 and `mushroom`=82.

It was found by building the port's own source for Linux as a yardstick (`tests/linux.sh`). The crash
showed up there, gfortran's run-time backtrace named the line (`8140 if(here(mushroom))goto 8143`), and a
check of every main-program variable outside the common blocks turned up the second one.

The fix belongs in the Multics master copy upstream. This port makes it in `mkwin.py` only.

## What else the port changes

- **No wait before a restored game.** On Multics, RESTORE turned away a game suspended less than 30 minutes
  before, and wanted a wizard for one less than 90 (`latncy`). `start` no longer makes that test.
  - SUSPEND still says "you will have to wait at least 90 minutes", which is the game's own text.
  - The other restriction, prime time, needed nothing. `mkunix.py` already builds the game with no hours
    set: in 1980 the cave was closed to all but wizards from 8:00 to 16:59 on weekdays. A wizard can still
    set hours in magic mode.
- **`ADV462_CLOCK="<day> <minute>"`** sets the clock, for test runs.
  - The day counts from 1 January 1977, as `datime` does, and the minute from midnight.
  - The clock then moves on a minute each time the game reads it, so the check at the 45th turn for a
    clock that stands still ("he's cheating") is not set off.
  - The clock seeds the random numbers, so a run with it set repeats exactly.
- **`advmsg`** prints the site routines' few messages through the game's own output unit, so they come out
  in order with its text. They use the Multics wording ("I can't find a suspended game called x.adv462.").

## Files

- **The game directory is the folder holding `adv462.exe`.** The program changes to it at start-up, so it
  finds `adventure.newgame` (and `adventure.data`, when there is no image) wherever it is started from.
- **SUSPEND *name*** writes `saves\name.adv462` there, and **RESTORE *name*** reads it.
  - A character Windows does not allow in a file name becomes `_`, as `.` and `/` do on Unix.
  - A DOS device name gets a `_` after it: `suspend con` writes `con_.adv462`.
  - A saved game is the raw common blocks. One made by another build, with other blocks, is refused.
- **Environment variables**, as on Unix, taken relative to the game directory:
  - `ADV462_DATA` is the database;
  - `ADV462_DIR` is the folder of `adventure.newgame`;
  - `ADV462_SAVEDIR` is the folder of saved games.
- **Magic mode**, the first command of a game, lets a wizard change the hours, the short game, the magic
  word, the latency and the message of the day, and then saves a new `adventure.newgame`. The magic word is
  `dwarf`, and the answer to "do you know what I thought it was?" is `no`, then `dwarf` again.

Two things the port leaves as they are, because every version does them:

- A RESTORE that finds no game asks "Are you a wizard?" and then starts a fresh game. That is Palter's
  flow, on Multics and Unix alike.
- The image holds `loc=-1`, left over from reading the database, so the first move reads `cond(-1)`. That
  is the word before `cond` in the same common block, so it does no harm. A bounds-checked build stops
  there, though.

## Checked (2026-09-28)

- **Played:** the opening, TAKE ALL and DROP ALL, FAST, FULL, LISTEN, TURNS, HOURS, `.`, SUSPEND, an
  immediate RESTORE, a RESTORE of a game that isn't there, QUIT with the score.
- **`tests/consoleplay.py`**, in a pseudo console (ConPTY), as `run.bat` runs it:
  - the text is on the screen before every read;
  - typed mixed case is played;
  - SUSPEND ends the program with exit 0, and RESTORE in a new window brings the game straight back;
  - QUIT and Ctrl-Z Enter end the program with exit 0.
- **`tests/fuzz.py`:** 200 runs with the clock set, 69,914 commands from the game's own vocabulary, with
  answers, overlong lines, TAKE and DROP ALL, and SUSPEND and RESTORE under odd names.
  - Each run suspends its first session and restores it in a second process. 115 of those RESTOREs found
    their game; in the rest the first session ended in the game's own ways (a death not reincarnated,
    QUIT).
  - No crash, hang or fatal error.
- **`tests/linux.sh`** builds the same source for Linux with Debian's gfortran and plays the same 200 runs:
  - all 200 transcripts are identical with the Windows program's;
  - the two programs' `adventure.newgame` are byte for byte the same.

Rerun the checks:

    python tests\fuzz.py
    wsl sh tests/linux.sh
    python tests\fuzz.py --compare .build\fuzz
    python tests\consoleplay.py
